## 5. Interface Analysis

### 5.1 run_benchmarks_v10.py -> custom_benchmark_v10.py

```
Run-Benchmark passes:
  --model-key    (e.g. "qwen3-coder-reap-25b-a3b-i1@iq4_xs")
  --api-model    (e.g. "qwen3-coder-reap-25b-a3b-i1@iq4_xs@q6_k")
  --sample-size  (int)
  --benchmark    ("DS1000" or "CoderEval")
  --qwen-prompt  (optional, only for qwen3.5)

custom_benchmark_v10.py expects:
  --non-interactive  (always set)
  --model-key        -> MODEL_CONFIG lookup
  --api-model        -> API call (MUST match lms ps)
```

**Risk:** If `api_model` does not match the exact load ID, LM Studio responds with HTTP 400. This is ensured by `model_info["_api_model"]` from `lms ps --json`.

### 5.2 run_benchmarks_v10.py -> lm_eval CLI

```
model_args = "base_url=...,model={api_model},num_concurrent=1"
  + optional parameters from _get_lmeval_params():
    - max_tokens, temperature, top_p, top_k, min_p, until

IMPORTANT: The model parameter MUST match the exact load ID.
  Example: "model=qwen3-coder-reap-25b-a3b-i1@iq4_xs@q6_k"
  Wrong:   "model=qwen3-coder-reap-25b-a3b-i1" (incomplete -> 400)
  Wrong:   "model=check" (invalid -> hangs)
```

### 5.3 csv_writer.py -> consolidate_results_v10.py

```
csv_writer writes:
  tasks_*.csv    -> FIELDNAMES = TASK_FIELDS (per-task)
  model_*.csv    -> FIELDNAMES = MODEL_FIELDS (aggregated)
  modell_*.csv   -> FIELDNAMES = SUMMARY_FIELDS (accumulated)
  konsolidiert_aktuell.csv -> CONSOLIDATED_FIELDS

consolidate_results_v10.py reads:
  read_custom_csv()      -> expects "score", "tokens_per_sec", "latency_s",
                             "cpu_during"/"cpu_pct", "gpu_during"/"gpu_pct"
  try_read_evalplus()    -> reads evalplus JSON files
  read_lmeval_per_model() -> reads lm_eval results_*.json
  read_agentic()         -> reads tool_eval_bench JSON
```

**Consistency problem:** `read_custom_csv()` looks for `cpu_during`/`gpu_during` (per-task fields), but the summary CSVs have `cpu_pct`/`gpu_pct`. This is correct, since `read_custom_csv()` is only intended for per-task CSVs (tasks_*.csv).

### 5.4 benchmark_config.py -> all scripts

```
DISPLAY_NAMES  -> consolidate_results_v10.py (lookup), run_all_dense.py (outdated)
WHITELIST      -> consolidate_results_v10.py (iterates over all models)
QUANT_MAP      -> consolidate_results_v10.py (_lookup_vram)
CAT_WEIGHTS    -> consolidate_results_v10.py (compute_category_scores)
OVERALL_WEIGHTS -> consolidate_results_v10.py (compute_category_scores)
PIPELINE_TIMEOUTS -> model_manager.py (imported), run_benchmarks_v10.py
```

## 6. Code Quality

### Strengths

1. **Clear responsibility separation:** Each script has a defined task
2. **Unified CSV schema:** All pipelines use csv_writer.py
3. **Type Hints:** All 3 main scripts have complete type hints
4. **Docstrings:** Detailed module and function documentation
5. **Error handling:** Retry mechanism, timeout scaling, fallback logic
6. **Tests:** 15 pytest tests for core functions

### Weaknesses

1. **`run_all_dense.py`:** WHITELIST manually maintained, not synchronized with benchmark_config.py
2. **`rerun_ds1000_mmlu.py`:** Model keys hardcoded (partially outdated)
3. **`get_available_models()` in custom_benchmark_v10.py:** Duplicates the function from run_benchmarks_v10.py (but with different return fields)
4. **`MetricsCollector` in custom_benchmark_v10.py:** Only used in `collect_system_metrics()`, but the class itself is inactive code (replaced by Monitor thread sampling)
5. **PowerShell redirect:** `run_all_dense.py` and `rerun_lmeval.py` redirect stdout/stderr to log files, but log files are not automatically rotated
